## 1. DATA CONTRACT GOVERNANCE

In accordance with **Architectural Invariant 7** (*Every subsystem must have a contract*) and **Invariant 8** (*Preserve provenance*), all data transitioning across subsystem boundaries in BlueOps must strictly conform to these published specifications.

Any modifications to these contracts require an updated schema version and backward-compatibility verification.

## 2. CONTRACT 1: CANONICAL EVENT SCHEMA (CES v1.0.0)

Every heterogeneous security event entering BlueOps (Windows Sysmon, Linux auditd, Suricata EVE) is transformed into this canonical format by the `EventNormalizationService`.

### 2.1 Java Class Definition: `com.blueops.telemetry.NormalizedEvent`
```java
public class NormalizedEvent {
    private String id;                       // UUID v4 of the normalized event
    private Instant timestamp;               // UTC event occurrence timestamp
    private EventMetadata event;             // Classification, provider, severity
    private HostMetadata host;               // Host identity, IP, OS, asset ID
    private UserMetadata user;               // User identity, domain, privileges
    private ProcessMetadata process;         // Process execution, PID, command line
    private NetworkMetadata network;         // Source/destination IPs, ports, proto
    private FileMetadata file;               // File paths, hashes, actions
    private Map<String, Object> additional;  // Unmapped vendor-specific attributes
    private String original;                 // Preserved raw, unparsed telemetry string
}
```

## 3. CONTRACT 2: SECURITY FINDING MODEL

Generated by `DetectionEvaluationService` upon matching an active Sigma rule, heuristic pattern, or threat intelligence indicator.

### 3.1 DTO Definition: `com.blueops.findings.FindingDto`
```java
public class FindingDto {
    private String findingId;               // e.g. "FND-D008-1001"
    private String ruleId;                  // e.g. "D008"
    private String ruleName;                // e.g. "Suspicious Encoded PowerShell Execution"
    private String ruleSeverity;            // "LOW", "MEDIUM", "HIGH", "CRITICAL"
    private String mitreTactic;             // e.g. "Execution"
    private String mitreTechniqueId;        // e.g. "T1059.001"
    private String mitreTechniqueName;      // e.g. "PowerShell"
    private String assetId;                 // e.g. "WIN-ASSET-001"
    private String assetName;               // e.g. "WIN-WORKSTATION-01"
    private Instant timestamp;              // Time detection fired
    private String status;                  // "UNASSIGNED", "LINKED_TO_INCIDENT", "DISMISSED"
    private String relatedDocId;            // Originating CES event UUID
    private Map<String, Object> details;    // Specific matching evidence (CLI, IP, hashes)
}
```

## 4. CONTRACT 3: CORRELATED ATTACK SCENARIO MODEL

Produced by `CorrelationEngine` when a multi-stage finding pattern matches within a sliding time window.

```java
public record CorrelatedScenario(
    String scenarioCode,                    // e.g. "C001"
    String title,                           // e.g. "Linux System Compromise Kill-Chain"
    String description,                     // Narrative of detected stages
```

## 5. CONTRACT 4: INCIDENT MODEL

Authoritative relational entity in PostgreSQL managing incident triage, findings, timeline, and analyst notes.

### 5.1 Relational Schema (`incidents` table)
```sql
CREATE TABLE incidents (
    id BIGSERIAL PRIMARY KEY,
    incident_number VARCHAR(64) UNIQUE NOT NULL, -- e.g. "INC-2026-0101"
    title VARCHAR(255) NOT NULL,
    description TEXT,
    severity VARCHAR(32) NOT NULL,              -- "LOW", "MEDIUM", "HIGH", "CRITICAL"
    status VARCHAR(32) NOT NULL,                -- "NEW", "ASSIGNED", "IN_PROGRESS", "CONTAINED", "CLOSED"
    primary_asset_id BIGINT REFERENCES assets(id),
    assigned_to VARCHAR(128),
    created_by VARCHAR(128) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL,
    resolved_at TIMESTAMP WITH TIME ZONE
);
```

### 5.2 Associated Join Entities
- `incident_findings`: Associates OpenSearch `finding_id` strings to the incident.
- `incident_notes`: Free-text investigative logs attributed to analyst or system.
- `incident_status_history`: Immutable log of every status transition with actor and timestamp.

## 7. CONTRACT 6: HOST RESPONSE AGENT PROTOCOL

Defines the cryptographically authenticated REST boundary between BlueOps Backend and the Python Response Daemon (`http://<endpoint>:5000/api/v1/action`).

### 7.1 Required HTTP Request Headers
```http
POST /api/v1/action HTTP/1.1
Host: 192.168.56.101:5000
Content-Type: application/json
X-Signature-SHA256: 7f83b1657ff1fc53b92dc18148a1d65dfc2d4b1fa3d677284addd200126d9069
X-Timestamp: 1763649310123
X-Nonce: 4c3d820b-2df9-4820-a65c-62cbf76d05f1
```

### 7.2 Request Payload
```json
{
  "action_uuid": "a81d4f2e-5f90-4a88-9d41-47128cb50022",
```
